# 第一轮评审(2026/11/4)

## 1.1
那我就从一个用户从注册到接收到对方用户单聊消息一点点说起吧 用户登录和注册是一样的 都是浏览器向logic节点发起的http请求 logic节点会查询数据库(如果是登录的话) 对比密码的hash值正确后为该用户创建一个token存在redis里面 为期24小时 主要用来确保ws连接建立的时候用户处于登录的状态 
此时web浏览器在接收到 http请求返回后向comet发起ws连接(向logic鉴权 unary 同步) comet也是维持ws连接的节点 当用户给其他用户发送消息时 浏览器返回的josn格式的包 comet拿到之后作简单的鉴权(是否登录后) 会将数据包和一些必要的字段 比如userid cometid一起打包给logic 此时用的是grpc调用 为了减少每次发送消息时重复的header帧 
grpc默认采用 双向流模式 用unary模式兜底 由线程池异步的向双向流w线程send消息 不阻塞io线程 通过pending request给r线程传回调 logic拿到数据后对数据进行再组织 维护唯一的session_id(通过redis) 维持对话有序性 并根据redis路由判断用户在线状态 最后将数据打包给kafka 由job端进行消费 拿出数据根据字段决定是否推送 是否落库
job和comet之间也是采用了 grpc 默认异步unary模式 可用cli-stream 最后由comet向对方推送消息


## 1.2
三个节点各司其职 高效处理各个节点的业务 为什么这么拆分？ 拿先假如只有一个节点 好处就是通讯简单 一个handle句柄流畅的走完整个链路 
但是高峰节点必然会损失性能 单节点既要维持ws长连接 还要处理业务逻辑 但是一边是维持连接的io线程 高io低cpu计算 一边是高cpu的业务线程 来回io线程等待业务逻辑执行 大大降低并发度
所以先把comet节点分出来 等logic业务逻辑处理完再给comet推送 这时logic节点的压力还是没有缓解 io线程等到任务异步交给logic了 自己是轻松了 logic线程完成大量业务处理还要推送回去 
这里就面临一个业务高峰 数据多的时候必然会在此堆积 怎么处理 再分一个节点job节点专门推送 持久化 这时logic给job的处理job明显处理慢 他需要等待回应 所以kafka排上用场了 不仅可以削峰
分区天然适合 job分开处理push请求和持久化落库 完事push专心向comet推送 也不用等落库
如果只保留两个节点的话 我会把comet和logic结合成一个节点 用线程池把业务逻辑和io线程分开



## 1.3
comet可以扩容 相当程度上提升并发度 把comet节点分布式部署 用户分布式连接 极大程度环节网络压力
logic不太好开多节点 但是也可以 需要共享redis和数据库 也要沟通好comet发给logic的请求 不能随便开跟分布式锁的争夺也有关系 可能争夺锁资源的开销和cpu密集型的处理相比划不来
job节点天然适合多分布式集群 由kafka解耦 可以高效拿到自己处理的消息 定点推送 持久化也都不需要添加过多的业务逻辑

## 1.4 
为什么要经过kafka上面也介绍过了 至于延迟还没有具体测试过 也确实有些场景是延迟不可接收的 比如要求送达速度 消息传递精准的 kafka解耦后导致消息还没push只是生产到kafka就返回了 这是一个缺点

## 1.5 
多台机器comet理论上是不需要通信的 所有业务处理可以无脑抛给logic logic知道comet的ip吧 job拿到消息的字段里面由有他需要push的comet字段



## 1.6 
我认为singlechat 和他们俩的最大区别就是 一个是点对点推送 另两个是发送后向所用room在线的用户一起推送 弹幕就是比room多两个字段 一个是视频id一个是时间戳

## 2.1 
在线情况 kafka key采取 session_id + comet_id 可以保证在一个comet会话里 消息的有序性 同时也保证了一定程度上的负载均衡 离线不用comet_id 是因为用户不在线没有具体的comet实例存在 

离线顺序保证性依靠的是msg_id 他在一个session里面是不重复严格递增的 以此维持该消息在此session的有序性
